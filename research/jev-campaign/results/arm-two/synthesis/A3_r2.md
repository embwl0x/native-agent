# Synthesis — packet A3

## 1. Summary

The packet covers two distinct regulatory threads in Chrome's extension platform. The first is the
Manifest V2 deprecation timeline, documented across three snapshots (2023-11, 2025-03-31,
2025-07-24) whose terms change materially between snapshots: the enterprise carve-out granted by
the `ExtensionManifestV2Availability` policy is progressively narrowed — from a full exemption
"until June 2025", to an exemption holding until the Chrome 139 branch, to the policy being removed
outright in Chrome 139. Answering "can users re-enable MV2?" correctly depends on which snapshot
you read: the 2025-03-31 source says yes, and the 2025-07-24 source says no as of Chrome 138. The
second thread is the declarativeNetRequest (DNR) limit regime, where limits were raised in Chrome
120 (rulesets) and Chrome 121 (dynamic rules) — but the Chrome 121 increase is scoped: it applies
only to rules whose action is `block`, `allow`, `allowAllRequests` or `upgradeScheme`, with
everything else still capped at 5,000. Across both threads the pattern is the same: a restriction
was relaxed or removed, but a narrower restriction survived the change and still binds. The packet
also contains a standing restriction with no change history in it at all — blocking `webRequest`
listeners are MV3-permitted only for policy-installed extensions.

## 2. Findings

1. **(f67dbbf9 + 095a5599 + 79250f1d — combination of three sources.)** The enterprise policy
   exemption was narrowed twice. f67dbbf9 (2023-11) grants enterprises using
   `ExtensionManifestV2Availability` "one additional year — until June 2025"; 095a5599 (2025-03-31)
   restates this as exempt "until at least June 2025" and names Chrome 138 as the final MV2-capable
   version when paired with the policy key; 79250f1d (2025-07-24) states the policy itself "will be
   removed with Chrome 139." *What changes if true:* an enterprise planning a migration should
   schedule it against the Chrome 139 branch, not against a calendar date in June 2025, and should
   treat f67dbbf9's date-based promise as superseded.

2. **(095a5599 vs 79250f1d — the same claim, answered differently by date.)** Whether users can
   manually re-enable MV2 extensions depends entirely on which source is current. 095a5599
   (2025-03-31) says MV2 is disabled by default but "users continue to be able to turn their
   Manifest V2 extensions back on"; 79250f1d (2025-07-24) says that with Chrome 138 "users can no
   longer turn them back on." *What changes if true:* any advice that tells a non-enterprise user to
   flip MV2 back on is wrong on Chrome 138 and later, and citing 095a5599 for it is citing a source
   that is no longer current.

3. **(79250f1d + 095a5599 — combination.)** Chrome 139 is a hard cutover, not a rollout. 095a5599
   contrasts it explicitly with the earlier gradual rollouts: "this change will impact all users on
   Chrome 139 at once"; 79250f1d agrees that it "will affect all users on Chrome 139
   simultaneously." *What changes if true:* there is no staged-percentage window to detect the
   breakage in, so migration must complete before the upgrade rather than in response to it.

4. **(05158f86.)** The Chrome 120 static-ruleset change raised the *simultaneously enabled* ceiling
   from 10 to 50, and the *total shipped* ceiling from 50 to 100 — two separate limits, both of
   which still exist as limits after the change. The source also notes the new figure is "significantly
   higher than the limit of 20 requested in the WECG." *What changes if true:* an extension can enable
   all 50 of a previously-offered 50-list set, but a design assuming an unbounded number of rulesets,
   or one exceeding 100 total, is still out of bounds.

5. **(2741637b + a65606cd — combination; the scope of the raise is the load-bearing part.)** The
   Chrome 121 increase to 30,000 dynamic rules is scoped to "safe" rules, defined by 2741637b as
   those with an action of `block`, `allow`, `allowAllRequests` or `upgradeScheme`. Both sources
   state the limit for all other (unsafe) dynamic rules remains 5,000, exposed as
   `MAX_NUMBER_OF_UNSAFE_DYNAMIC_RULES`, and a65606cd adds that unsafe rules added within that 5,000
   also count toward the 30,000. *What changes if true:* a budget calculation must classify rules by
   action before sizing, and cannot treat 30,000 as a general dynamic-rule allowance.

6. **(a65606cd.)** Session rules are capped at 5,000 (`MAX_NUMBER_OF_SESSION_RULES`), and before
   Chrome 120 that 5,000 was a *combined* dynamic-and-session budget — after Chrome 120 the two are
   separate pools. *What changes if true:* an extension targeting Chrome 120+ can hold 5,000 session
   rules without that consuming its dynamic-rule allowance, which is a real gain over pre-120
   behavior.

7. **(688c66f7.)** Blocking `webRequest` is not removed in MV3 but is scope-restricted: the
   `webRequestBlocking` permission is "only available to policy installed extensions," and a
   blocking handler requires both `webRequest` and `webRequestBlocking` in the manifest. *What
   changes if true:* an extension distributed through the Chrome Web Store cannot rely on this path
   and must use declarativeNetRequest, while an enterprise shipping by policy can.

8. **(05158f86 + 2741637b vs 095a5599 + 79250f1d — cross-thread observation.)** The two 2023-11
   blog sources describe limits that were *raised* and remain accurate as forward-looking statements
   (the Chrome 120/121 ships happened and are confirmed by the 2025-06 API reference a65606cd),
   whereas the 2023-11 MV2 source f67dbbf9 describes a deadline that was *superseded*. *What changes
   if true:* age alone does not determine which sources are stale here — a 2023 blog post can still
   be the correct citation for a limit, while another 2023 post from the same month is not a safe
   citation for a deadline.

## 3. What you could not determine

- **Whether the policy still functions on Chrome 138 in the strict sense.** 095a5599 says Chrome 138
  is the last version to support MV2 "when paired with the `ExtensionManifestV2Availability` key,"
  and 79250f1d says the policy is removed in 139 — together these imply the policy works on 138,
  but 79250f1d's flat statement that "with Chrome 138 all users on all channels have MV2 extensions
  disabled" is not explicitly qualified to exclude policy-managed fleets. The packet does not settle
  the wording.
- **Whether anything exists after Chrome 139.** No source in the packet describes any successor
  policy, extended enterprise escape hatch, or post-139 state beyond "cease to function."
- **Static rule count limits.** The packet gives ruleset *counts* (05158f86) and dynamic/session
  *rule* counts (2741637b, a65606cd), but never states how many rules a static ruleset may contain,
  nor any limit specific to regex rules.
- **Remotely hosted code.** The packet contains nothing on whether MV3 permits executing code
  fetched at runtime.
- **Review or publishing timelines.** No source addresses Chrome Web Store review duration or how
  the nature of an update affects it.
- **Firefox and Safari specifics.** 05158f86 says both "provided early input" and support raising
  the limits, but the packet does not state what limits those browsers actually enforce.
