# Synthesis — A1

## Summary

The packet covers two distinct regimes: the removal of Manifest V2 from Chrome, and the
quantitative limits on Manifest V3's declarativeNetRequest (DNR) filtering API, plus one
surviving exception in the blocking webRequest API. Two things changed and the packet
records both the old and new state: the MV2 enterprise exemption (policy-based, ends with
Chrome 139) and the DNR rule ceilings (raised in Chrome 120 for static rulesets and in
Chrome 121 for a defined subset of "safe" dynamic rules). Two restrictions survived those
changes untouched: the 5,000-rule ceiling for all non-safe dynamic rules, and the 1,000-rule
cap on regex rules per type. One exception is scoped by installation method rather than by
version: blocking webRequest handlers remain available in MV3 only to policy-installed
extensions. The packet contains one pair of sources on the same topic where the older one is
no longer current — 095a5599 (2025-03-31) versus 79250f1d (2025-07-24) — and answering from
the older one produces a wrong answer about whether users can re-enable MV2 extensions.

## Findings

1. **Sources: 095a5599 + 79250f1d (combination).** These two describe the same MV2 timeline
   at different dates, and the later one supersedes the earlier on a checkable point. 095a5599
   (2025-03-31) states MV2 extensions are disabled by default but "users continue to be able to
   turn their Manifest V2 extensions back on"; 79250f1d (2025-07-24) states that with Chrome 138
   "Users can no longer turn them back on." Anyone relying on 095a5599 for current behavior would
   wrongly tell a user they can re-enable an MV2 extension on 138.

2. **Sources: 095a5599 + 79250f1d (combination).** Both agree the enterprise exemption is
   version-bounded, not permanent: the ExtensionManifestV2Availability policy exempts enterprises
   (095a5599: "until at least June 2025"), Chrome 138 is the last version where it works, and the
   policy is removed with Chrome 139, affecting all users on 139 at once rather than by gradual
   rollout. An enterprise would plan a hard cutover — MV2 extensions stop functioning on upgrade
   to 139 — rather than a phased one.

3. **Source: 2741637b.** The 30,000-rule dynamic ceiling introduced in Chrome 121 is scoped by
   action type, not granted generally: it applies only to "safe" DNR rules, defined as rules whose
   action is `block`, `allow`, `allowAllRequests` or `upgradeScheme` (exposed as
   MAX_NUMBER_OF_DYNAMIC_RULES). A developer would check the action of each rule before assuming
   headroom above 5,000.

4. **Sources: 2741637b + a65606cd (combination).** The pre-existing 5,000 limit survived the
   Chrome 121 increase and still binds all other dynamic rules — 2741637b: "The rule limit for all
   other dynamic net request rules stays at 5,000"; a65606cd exposes it as
   MAX_NUMBER_OF_UNSAFE_DYNAMIC_RULES and adds that unsafe rules added within that 5,000 also count
   toward the 30,000. A developer would budget unsafe rules against 5,000 and treat them as
   consuming safe-rule headroom too, not as a separate pool.

5. **Source: a65606cd.** Session rules are capped at 5,000 (MAX_NUMBER_OF_SESSION_RULES), and
   before Chrome 120 dynamic and session rules shared a single combined 5,000 limit; that pooling
   no longer applies. An extension targeting Chrome 120+ would size dynamic and session rule sets
   independently rather than against one shared budget.

6. **Sources: 05158f86 + 7c82d4f5 (combination).** The static-ruleset increase announced for
   Chrome 120 is confirmed as the current documented state: 05158f86 (2023-11) announces a move
   from 10-of-50 to 50 enabled and 100 total; 7c82d4f5 (2025-06) documents exactly 100 declarable
   in `rule_resources` with 50 enabled at a time (MAX_NUMBER_OF_ENABLED_STATIC_RULESETS). The
   older blog post's *new* numbers are still current; only its "until recently" figures are
   historical, so it is safe to cite for the limits but not for present-day baselines.

7. **Source: 7c82d4f5.** Enabled static rulesets are collectively guaranteed at least 30,000
   rules (GUARANTEED_MINIMUM_STATIC_RULES) — a floor, stated as "at least", not a ceiling. A
   developer would treat 30,000 as the number they can count on, and would not read it as the
   maximum.

8. **Source: 7c82d4f5.** Two restrictions apply to static rules regardless of the ruleset
   increases: regex rules of each type are capped at 1,000 (MAX_NUMBER_OF_REGEX_RULES), and each
   rule must compile to under 2KB. A team planning a large regex-driven ruleset would have to
   convert most rules to non-regex matching.

9. **Source: 688c66f7.** Blocking webRequest is not removed in MV3 but is narrowed by scope:
   the `webRequestBlocking` permission is "only available to policy installed extensions", and a
   blocking handler needs both `webRequest` and `webRequestBlocking` in the manifest. A developer
   shipping through the public store would design around declarativeNetRequest; an enterprise
   deploying by policy could still register a blocking listener.

## What you could not determine

- **Remotely hosted code.** The packet says nothing about whether MV3 extensions may fetch and
  execute code from a developer's server, or what alternatives (e.g. remote configuration or
  data) are allowed. Nothing in these seven sources touches it.
- **Review timelines.** No source addresses Chrome Web Store review, expedited paths for
  rule-file-only updates, or what would make such an expectation hold or fail.
- **Whether the "safe rules" definition also governs static rules.** 2741637b and a65606cd frame
  the safe/unsafe split for dynamic rules; 7c82d4f5 describes static limits without using that
  vocabulary. The packet does not state whether static rules are partitioned the same way.
- **Whether MV2 removal has exceptions after Chrome 139.** 79250f1d says the policy is removed
  and MV2 extensions cease to function; the packet does not say whether any channel, platform, or
  extended-support build retains MV2 beyond that.
- **The exact Chrome 138/139 MV2 state as of any date after 2025-07-24.** 79250f1d is the most
  recent source here; whether anything changed after it is outside the packet.
- **Interaction between the 30,000 static guarantee and the 30,000 safe-dynamic limit.** Both
  numbers appear, but the packet does not say whether they are independent budgets.

## Frozen question set

**Q1.** Yes — on Chrome 138 with ExtensionManifestV2Availability set, MV2 extensions still run;
138 is explicitly the final version that supports them when paired with that policy key. Once the
fleet moves to Chrome 139 the policy is removed and MV2 extensions cease to function, and the
change hits all users on 139 simultaneously rather than rolling out gradually.
*Sources: 095a5599, 79250f1d.*

**Q2.** No. `redirect` is not among the actions defined as "safe" (`block`, `allow`,
`allowAllRequests`, `upgradeScheme`), so redirect rules fall under the unsafe dynamic ceiling of
5,000 (MAX_NUMBER_OF_UNSAFE_DYNAMIC_RULES), not the 30,000 safe limit added in Chrome 121; any
unsafe rules within that 5,000 also count against the 30,000.
*Sources: 2741637b, a65606cd.*

**Q3.** No. The total number of regular expression rules of each type cannot exceed 1,000
(MAX_NUMBER_OF_REGEX_RULES), so 4,000 is over the cap; additionally each rule must be under 2KB
once compiled. Regex is available to all rule types, but only within that 1,000 per-type ceiling.
*Source: 7c82d4f5.*

**Q4.** Yes, but only for policy-installed extensions — as of Manifest V3 the
`webRequestBlocking` permission required to register blocking event handlers is available only to
them, and the manifest must declare both `webRequest` and `webRequestBlocking`.
*Source: 688c66f7.*
