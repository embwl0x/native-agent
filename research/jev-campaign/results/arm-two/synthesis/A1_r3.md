# Synthesis — A1

## 1. Summary

The packet covers two separate regimes: the end of Manifest V2 support in Chrome, and the
quantitative limits of the declarativeNetRequest (DNR) API that MV3 filtering extensions must
live within. On MV2, the packet contains two snapshots of the same page (095a5599, 2025-03-31;
79250f1d, 2025-07-24) that describe the same endpoint by different routes: the earlier one is
forward-looking and partly stale (it still says users can turn MV2 extensions back on), the later
one is current (users can no longer re-enable, and the enterprise
`ExtensionManifestV2Availability` policy — the last remaining exemption — is removed in Chrome
139). On DNR, the packet shows limits that were deliberately raised (enabled static rulesets, safe
dynamic rules) alongside limits that survived those raises untouched (unsafe dynamic rules at
5,000; regex rules at 1,000 per type; 2KB per compiled rule). The raised limits are scoped: the
30,000 dynamic figure applies only to rules whose action is `block`, `allow`, `allowAllRequests`
or `upgradeScheme`. The 2023-11 blog post (05158f86, 2741637b) is the announcement of changes
that the 2025-06 reference pages (7c82d4f5, a65606cd) now state as current, so the blog is
reliable as history but should not be quoted for present numbers.

## 2. Findings

1. **MV2 support ends at a hard version boundary, not a gradual rollout** — rests on 79250f1d,
   corroborated and dated by 095a5599 (combination of two sources). Both state that support is
   removed in the Chrome 139 branch and that the change hits all users on 139 at once, unlike the
   earlier staged disabling. *Consequence:* an enterprise plans a migration against a version pin,
   not against a percentage rollout.
2. **The enterprise policy exemption is scoped and now expired** — rests on 095a5599 and 79250f1d
   (combination). 095a5599 says enterprises using `ExtensionManifestV2Availability` are exempt
   "until at least June 2025" and that Chrome 138 is the final version supporting MV2 when paired
   with that key; 79250f1d says the policy is removed with Chrome 139. *Consequence:* a fleet
   treats 138 as the last usable pin and stops relying on the policy as a long-term control.
3. **095a5599 is no longer current on user re-enablement** — rests on 095a5599 vs. 79250f1d
   (combination). 095a5599 says users "continue to be able to turn their Manifest V2 extensions
   back on"; 79250f1d says that with Chrome 138 users "can no longer turn them back on."
   *Consequence:* anyone answering "can a user re-enable MV2?" from the March snapshot gets it
   wrong; the July snapshot governs.
4. **The 30,000 dynamic-rule limit is action-scoped, and the 5,000 limit survives for everything
   else** — rests on 2741637b and a65606cd (combination). 2741637b defines "safe" rules as those
   with an action of `block`, `allow`, `allowAllRequests` or `upgradeScheme` and says the limit for
   all other dynamic rules stays at 5,000; a65606cd names the two constants
   (`MAX_NUMBER_OF_DYNAMIC_RULES` = 30,000 from Chrome 121, `MAX_NUMBER_OF_UNSAFE_DYNAMIC_RULES`
   = 5,000) and adds that unsafe rules added within the 5,000 allowance also count toward the
   30,000. *Consequence:* a developer counts unsafe-action rules (e.g. redirect, modifyHeaders)
   against 5,000 separately rather than assuming a flat 30,000 budget.
5. **Regex rules are capped far below the general rule budget, and that cap was not raised** —
   rests on 7c82d4f5. The total number of regular-expression rules of each type cannot exceed
   1,000 (`MAX_NUMBER_OF_REGEX_RULES`), and each rule must be under 2KB once compiled — stated in
   the current 2025-06 reference alongside the raised static limits. *Consequence:* a ruleset
   design converts most regex patterns to non-regex matching rather than scaling regex count.
6. **Static ruleset limits were raised, and the reference confirms the raise stuck** — rests on
   05158f86 and 7c82d4f5 (combination). The 2023-11 blog announced moving from 10-of-50 to
   50-enabled and 100 total, shipping in Chrome 120; the 2025-06 reference states 100 declarable
   via `rule_resources` with 50 enabled at a time (`MAX_NUMBER_OF_ENABLED_STATIC_RULESETS`) and a
   `GUARANTEED_MINIMUM_STATIC_RULES` of 30,000 collectively. *Consequence:* an extension can ship
   list variety up to 100 and let users enable up to 50, but budgets rules against a 30,000
   guaranteed floor.
7. **Session rules are a separate 5,000 budget, no longer shared with dynamic rules** — rests on
   a65606cd. `MAX_NUMBER_OF_SESSION_RULES` is 5,000; before Chrome 120 there was a single combined
   dynamic-plus-session limit of 5,000. *Consequence:* on Chrome 120+, a developer stops
   subtracting session rules from the dynamic allowance.
8. **Blocking webRequest survives in MV3 only inside a named scope** — rests on 688c66f7. The
   `webRequestBlocking` permission is required to register blocking handlers and, as of MV3, is
   only available to policy-installed extensions; the handler also needs the `webRequest`
   permission. *Consequence:* a consumer/Web-Store extension designs on DNR, while an
   enterprise-deployed one may still use blocking webRequest.
9. **The 2023-11 blog is history, not current specification** — rests on 05158f86 and 2741637b
   against 7c82d4f5 and a65606cd (combination). The blog's numbers are phrased as forthcoming
   ("shipping in Chrome 120", "starting with Chrome 121"); the 2025-06 references restate them as
   present-tense constants. *Consequence:* cite the API reference for a current limit and the blog
   only when explaining when or why a limit changed.

## 3. What you could not determine

- Whether any MV2 escape hatch exists after Chrome 139 (other enterprise policies, forks,
  extended-support channels). 79250f1d states the policy is removed; the packet says nothing
  about alternatives.
- Whether the raised DNR limits actually shipped in Firefox and Safari. 05158f86 says both
  "provided early input" and supported the proposal — support for the proposal is not evidence of
  implementation, and no Firefox or Safari source is in the packet.
- What counts as "unsafe" beyond the four named safe actions. The packet defines safe actions
  exhaustively by enumeration but never lists the unsafe ones, so classifying a specific action
  (e.g. `modifyHeaders`) is inference from the enumeration, not a stated fact.
- Whether `GUARANTEED_MINIMUM_STATIC_RULES` (30,000) is a floor that can be exceeded in practice
  and under what conditions. 7c82d4f5 says "guaranteed at least" without stating the mechanism or
  ceiling.
- Remote-code execution rules for MV3, and Chrome Web Store review timelines. Nothing in the
  packet addresses either.
- Whether the regex cap of 1,000 "of each type" is counted per rule-action-type, per ruleset, or
  per extension. 7c82d4f5's wording does not resolve this.

## Frozen question set

**Q1.** On Chrome 138 with `ExtensionManifestV2Availability` set, the fleet's Manifest V2
extensions still run — 138 is explicitly the final version of Chrome to support MV2 when paired
with that key. Once the fleet moves to Chrome 139 the policy is removed and MV2 extensions cease
to function, for all users on 139 at once rather than by staged rollout.
*Sources: 095a5599, 79250f1d.*

**Q2.** No. Redirect is not among the actions defined as "safe" (`block`, `allow`,
`allowAllRequests`, `upgradeScheme`), so redirect rules fall under
`MAX_NUMBER_OF_UNSAFE_DYNAMIC_RULES`, which stays at 5,000; the 30,000
`MAX_NUMBER_OF_DYNAMIC_RULES` ceiling available from Chrome 121 covers only safe rules, and any
unsafe rules used within the 5,000 allowance also count against that 30,000.
*Sources: 2741637b, a65606cd.*

**Q3.** No. The total number of regular-expression rules of each type cannot exceed 1,000
(`MAX_NUMBER_OF_REGEX_RULES`), so roughly 4,000 is four times the cap; additionally each rule —
regex or not — must be less than 2KB once compiled.
*Source: 7c82d4f5.*

**Q4.** Yes, but only in a narrow scope: registering a blocking event handler requires the
`webRequestBlocking` permission, which as of Manifest V3 is available only to policy-installed
extensions, and the handler also requires the `webRequest` permission in the manifest.
*Source: 688c66f7.*
