# Synthesis — packet A1

## Summary

The packet covers two regulated areas: the end of Manifest V2 support in Chrome, and the
quantitative limits on the declarativeNetRequest (DNR) filtering API, plus one narrow
survival of the old blocking webRequest API. Across both areas the pattern is the same —
limits were raised or removed at named Chrome versions (120, 121, 138, 139), and several of
the excerpts describe the state *before* one of those cutovers. Two sources (05158f86 and
095a5599, both pre-dating their own subject's cutover) are no longer current and would give
a wrong answer if used on their own; each has a later source in the packet that supersedes
it (7c82d4f5 / a65606cd, and 79250f1d respectively). The DNR limits that survived every
change and still bind are the regex-rule ceiling (1,000 per type), the 2KB compiled rule
size, the 5,000 session-rule cap, and the 5,000 cap on *unsafe* dynamic rules — the raised
30,000 ceiling is scoped strictly to the four "safe" actions. The webRequestBlocking
exception survives into MV3 but only inside the named scope of policy-installed extensions.

## Findings

1. **(095a5599 + 79250f1d, combined.)** 095a5599 (2025-03-31) states enterprises using
   `ExtensionManifestV2Availability` are exempt "until at least June 2025" and that the
   Chrome 139 branch *will begin* in June; 79250f1d (2025-07-24) states the policy *will be
   removed with Chrome 139* and MV2 extensions cease to function on upgrade. The later
   source resolves the earlier one's open-ended "at least": the exemption ends with 139, it
   is not extended. Anyone answering enterprise MV2 questions from 095a5599 alone would
   wrongly leave the end date open — consult 79250f1d.

2. **(095a5599 + 79250f1d, combined.)** Both agree Chrome 138 is the last version on which
   MV2 extensions work, but they differ on the non-enterprise state at 138: 095a5599 says
   users "continue to be able to turn their Manifest V2 extensions back on," while 79250f1d
   says that at Chrome 138 "users can no longer turn them back on." The user-level toggle
   was withdrawn between the two dates. A support answer written from 095a5599 would tell a
   consumer user to re-enable an extension that can no longer be re-enabled.

3. **(79250f1d.)** The Chrome 139 change is simultaneous for all users, not a staged
   rollout (095a5599 says the same, contrasting it with the "gradual" earlier changes).
   A fleet planning a migration cannot rely on being in a late rollout cohort — the cutover
   lands the moment the fleet takes 139.

4. **(05158f86 + 7c82d4f5, combined.)** 05158f86 (2023-11) describes the pre-Chrome-120
   state (50 rulesets shipped, 10 enabled) and announces the new limits as forthcoming;
   7c82d4f5 (2025-06) documents the shipped state: up to 100 static rulesets declared in
   `rule_resources`, 50 enabled at once (`MAX_NUMBER_OF_ENABLED_STATIC_RULESETS`), with at
   least 30,000 rules guaranteed collectively (`GUARANTEED_MINIMUM_STATIC_RULES`). Quoting
   05158f86's "50 lists / 10 enabled" as current would understate the budget by 5x — the
   current figures come from 7c82d4f5.

5. **(2741637b + a65606cd, combined.)** The 30,000-rule dynamic limit
   (`MAX_NUMBER_OF_DYNAMIC_RULES`, Chrome 121 onward) is scoped by action, not by volume:
   it applies only to "safe" rules, defined as `block`, `allow`, `allowAllRequests` and
   `upgradeScheme`. Every other action stays at 5,000
   (`MAX_NUMBER_OF_UNSAFE_DYNAMIC_RULES`), and a65606cd adds that unsafe rules added within
   that 5,000 *also count against* the 30,000. An extension using `redirect` or
   `modifyHeaders` should budget 5,000, not 30,000.

6. **(a65606cd.)** Session rules are capped at 5,000 (`MAX_NUMBER_OF_SESSION_RULES`) with
   no safe/unsafe split stated; separately, the pre-Chrome-120 rule that dynamic and session
   rules shared a single 5,000 budget is gone. Post-120 an extension can hold 5,000 session
   rules *and* its dynamic allotment rather than splitting one pool.

7. **(7c82d4f5.)** Two static-rule constraints survived every limit increase and still
   bind: regular-expression rules cannot exceed 1,000 *of each type*
   (`MAX_NUMBER_OF_REGEX_RULES`), and each rule must be under 2KB once compiled. A ruleset
   designed against the raised 30,000 guarantee still has to keep regex rules under 1,000
   and convert the excess to non-regex matching.

8. **(688c66f7.)** Blocking webRequest was not removed in MV3, it was narrowed: the
   `webRequestBlocking` permission "is only available to policy installed extensions," and a
   blocking handler needs both `webRequest` and `webRequestBlocking`. An enterprise-deployed
   extension can still use it; the same code shipped through the public store cannot.

9. **(2741637b, a65606cd, 05158f86, 79250f1d.)** The whole packet is version-gated: correct
   answers depend on knowing the Chrome version in play (120 for ruleset counts and the
   dynamic/session pool split, 121 for the safe-rule limit, 138/139 for MV2). Any answer
   given without pinning a version is unreliable.

## What you could not determine

- Whether anything *other* than removal of the `ExtensionManifestV2Availability` policy
  distinguishes enterprise from consumer behaviour at Chrome 139; the packet says only that
  the policy is removed and all users are affected at once.
- Whether the static-rule guarantee of 30,000 (`GUARANTEED_MINIMUM_STATIC_RULES`) has a
  higher actual ceiling, or what happens when a ruleset exceeds it — "guaranteed at least"
  is not defined further.
- Whether the 1,000 regex ceiling applies separately to static, dynamic and session rules,
  or "of each type" means each *action* type. 7c82d4f5 states it only in the static-rule
  context.
- Whether session rules have a safe/unsafe distinction like dynamic rules; a65606cd states
  one flat 5,000 figure.
- Nothing in the packet addresses remotely hosted code, extension review timelines, or
  Chrome Web Store policy.

## Frozen question set

**Q1.** On Chrome 138 with `ExtensionManifestV2Availability` set, the fleet's Manifest V2
extensions do still run — 138 is the final version that supports MV2 when paired with that
policy key, and enterprises remained exempt from the browser-level changes. Once the fleet
moves to Chrome 139 the policy is removed entirely and MV2 extensions cease to function, for
all users at once rather than by staged rollout.
Sources: 79250f1d, 095a5599.

**Q2.** No. `redirect` is not one of the four actions defined as "safe" (`block`, `allow`,
`allowAllRequests`, `upgradeScheme`), so redirect rules fall under
`MAX_NUMBER_OF_UNSAFE_DYNAMIC_RULES`, which stays at 5,000; the 30,000
`MAX_NUMBER_OF_DYNAMIC_RULES` ceiling introduced in Chrome 121 is reserved for safe rules,
and any unsafe rules added within the 5,000 also count against that 30,000.
Sources: 2741637b, a65606cd.

**Q3.** No. The total number of regular-expression rules of each type cannot exceed 1,000
(`MAX_NUMBER_OF_REGEX_RULES`), so 4,000 is four times over the limit; additionally each rule
must be less than 2KB once compiled. This ceiling is independent of the 30,000
`GUARANTEED_MINIMUM_STATIC_RULES` budget for static rulesets.
Source: 7c82d4f5.

**Q4.** Yes, but only if it is a policy-installed extension — as of Manifest V3 the
`webRequestBlocking` permission is available only to policy installed extensions, and
registering a blocking handler requires both the `webRequest` and `webRequestBlocking`
permissions in the manifest.
Source: 688c66f7.
