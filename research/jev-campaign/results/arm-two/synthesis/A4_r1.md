# Synthesis — packet A4

## Summary

The packet covers two distinct regimes: the Manifest V2 phase-out timeline and the
declarativeNetRequest (DNR) rule and ruleset limits that replaced blocking webRequest.
Across the set, several restrictions were relaxed rather than removed — static ruleset
limits rose in Chrome 120, dynamic rule limits rose in Chrome 121 but only for a named
subset of rule actions, and the combined dynamic+session ceiling that existed before
Chrome 120 was split into separate ceilings. One restriction survived every relaxation:
blocking webRequest listeners remain available in MV3 only to policy-installed
extensions. The MV2 timeline is the place where currency matters most — the 2023-11
source (f67dbbf9) states the enterprise-policy grace period but predates the concrete
removal mechanics, which only the 2025-03-31 source (095a5599) supplies. The packet
says nothing about regex rule limits or remote-code execution, so questions in those
areas cannot be answered from it.

## Findings

1. **Static ruleset limits were raised in Chrome 120, changing both the enabled and the
   total ceiling** (05158f86). Before that change extensions could ship 50 static
   rulesets with 10 enabled simultaneously; from Chrome 120 it is 50 enabled out of 100
   total. *Consequence:* an extension author targeting Chrome 120+ can offer users five
   times as many concurrently active filter lists without shipping a second extension.

2. **The dynamic rule ceiling is action-dependent, not a single number**
   (2741637b + a65606cd, combined). Chrome 121 introduced a 30,000-rule limit
   (MAX_NUMBER_OF_DYNAMIC_RULES) that applies only to "safe" rules, explicitly defined
   as those with an action of `block`, `allow`, `allowAllRequests` or `upgradeScheme`;
   all other dynamic rules stay at 5,000 (MAX_NUMBER_OF_UNSAFE_DYNAMIC_RULES), and
   unsafe rules added within that 5,000 also count against the 30,000. *Consequence:* a
   developer must budget by rule action, not by rule count, and cannot assume headroom
   of 30,000 for rules like redirect or modifyHeaders.

3. **The pre-Chrome-120 combined dynamic+session ceiling no longer exists** (a65606cd).
   Before Chrome 120 there was a single 5,000-rule limit covering dynamic and session
   rules together; now session rules have their own 5,000 limit
   (MAX_NUMBER_OF_SESSION_RULES) separate from the dynamic limits. *Consequence:* an
   extension can hold 5,000 session rules without those rules eating into its dynamic
   rule budget.

4. **Blocking webRequest survived the MV3 transition, but only inside a named scope**
   (688c66f7). The `webRequestBlocking` permission is, as of Manifest V3, available
   only to policy-installed extensions, and a blocking handler needs both `webRequest`
   and `webRequestBlocking` in the manifest. *Consequence:* a team building an
   enterprise-deployed extension can still use blocking listeners, while the same code
   in a Web Store extension cannot.

5. **The total static rule budget and the dynamic addition are stated together as
   330,000 + 30,000** (e8621005). This is the aggregate rule figure, distinct from the
   ruleset-count figures in 05158f86. *Consequence:* capacity planning should treat
   ruleset count and rule count as two separate ceilings that must both be satisfied.

6. **Review skipping applies only to safe changes confined to static DNR rule lists**
   (e8621005). If the only changes in an update are safe modifications to the
   extension's static DNR rule list, Chrome approves the update in minutes. *Consequence:*
   a filter-list refresh can ship on a minutes-long cycle, but any other change in the
   same update forfeits that path.

7. **Manifest V2 support ends at a version boundary, not a gradual rollout**
   (095a5599). MV2 extensions are disabled by default on all channels with users able
   to re-enable them; support is removed in the Chrome 139 branch, and that removal
   affects all users on 139 at once, making Chrome 138 the final MV2-supporting version
   when paired with the ExtensionManifestV2Availability key. *Consequence:* an
   enterprise treats the 138→139 upgrade as a hard cutover date rather than a staged
   window.

8. **The enterprise exemption is a deadline that the older source states and the newer
   source terminates** (f67dbbf9 + 095a5599, combined). f67dbbf9 (2023-11) grants
   ExtensionManifestV2Availability users until June 2025 and says policy-enabled
   browsers are not impacted by the deprecation rollout until then; 095a5599
   (2025-03-31) restates the exemption as "until at least June 2025" and then supplies
   the mechanism that ends it — the Chrome 139 branch beginning in June. *Consequence:*
   anyone answering "does the policy still protect us?" from f67dbbf9 alone would miss
   that the protection expires at a specific browser version, so the 2023 source must
   not be used on its own for any post-June-2025 question.

9. **Two sources dated 2023-11 describe limits that only took effect in later Chrome
   versions** (05158f86 shipping in Chrome 120; 2741637b starting with Chrome 121).
   The publication date therefore does not indicate when the behavior became available.
   *Consequence:* a developer must gate on Chrome version, not on the age of the
   announcement, when deciding whether a limit is in force.

## What you could not determine

- **Regex rules.** The packet never mentions regex-based filter rules, any
  MAX_NUMBER_OF_REGEX_RULES constant, or any constraint specific to regex rules
  (length, complexity, count). Nothing in the set establishes whether regex rules are
  counted within the 330,000 static budget or against a separate ceiling.
- **Remote code / remotely hosted code.** No source in the packet addresses executing
  code fetched at runtime, remotely hosted code policy, or any permitted exception
  (e.g. remote configuration data).
- **What "safe modifications" means for review skipping.** e8621005 uses "safe
  modifications" for static rule updates, and 2741637b defines "safe" for DNR rules by
  action type, but the packet does not state that the review-skipping definition is the
  same definition. The two may or may not coincide.
- **Whether the review-skipping path has an SLA.** "In minutes" is the stated
  expectation; the packet gives no guaranteed time, no failure mode, and no statement of
  what happens when a change is judged unsafe.
- **Post-Chrome-139 enterprise state.** 095a5599 says support is removed in 139; the
  packet does not say whether any policy, flag, or enterprise channel exists after that
  point.
- **Whether the 2023-11 ruleset limits in 05158f86 were later changed again.** The most
  recent DNR reference in the packet (a65606cd, 2025-06) covers dynamic and session
  rules but does not restate the ruleset counts, so their current status is not
  confirmed by a 2025 source.
