# Synthesis — packet A3

## Summary

The packet covers two distinct restriction regimes in Chrome extensions: the end-of-life
timeline for Manifest V2 (with an enterprise policy exception that is itself time-boxed),
and the numeric rule limits of the declarativeNetRequest (DNR) API. Both regimes changed
over the period the sources cover, and in both cases the packet contains an older source
that was correct when written and is now superseded. For MV2, the 2023 blog post
(f67dbbf9) grants enterprises using `ExtensionManifestV2Availability` an exemption "until
June 2025"; the 2025 timeline entries (095a5599, 79250f1d) resolve that into a hard
boundary — Chrome 138 is the last version where the policy works, and the policy itself is
removed in Chrome 139. For DNR, the older 10-of-50 static ruleset limits (05158f86) were
raised to 50-of-100 in Chrome 120, and the dynamic rule ceiling was split in Chrome 121
into a 30,000 "safe" limit and a retained 5,000 limit for everything else (2741637b,
a65606cd). The one restriction in the packet that survived every change unchanged is the
blocking `webRequest` restriction: under MV3 it remains available only to policy-installed
extensions (688c66f7). The packet says nothing about regex rule limits, remote code
execution, or review timelines.

## Findings

1. **(f67dbbf9 + 095a5599 + 79250f1d, combined)** The enterprise `ExtensionManifestV2Availability`
   exemption is not a standing carve-out but a deferral with a terminal date. f67dbbf9
   (2023-11) promises "one additional year — until June 2025"; 095a5599 (2025-03-31) restates
   it as "until at least June 2025" and names Chrome 138 as the final supporting version;
   79250f1d (2025-07-24) states the policy is removed with Chrome 139. Anyone relying on
   f67dbbf9 alone would plan a migration deadline of June 2025 without knowing the exact
   version cut-off — the combination fixes it at the 138→139 boundary.
   *Do differently:* pin migration planning to the Chrome 139 rollout, not to a calendar month.

2. **(095a5599 + 79250f1d, combined)** The MV2 disablement for ordinary users and the removal
   for enterprises are separate events. 095a5599 says users can still re-enable disabled MV2
   extensions; 79250f1d says that as of Chrome 138 users can no longer turn them back on.
   Only the second reflects current state for non-enterprise users.
   *Do differently:* do not tell users they can re-enable an MV2 extension on Chrome 138+.

3. **(79250f1d)** The Chrome 139 change is non-gradual: it "will affect all users on Chrome 139
   simultaneously," unlike the earlier staged rollouts. 095a5599 makes the same point.
   *Do differently:* do not assume a percentage rollout window in which to react.

4. **(688c66f7)** Blocking `webRequest` is not removed under MV3 — it is scoped. The
   `webRequestBlocking` permission is "only available to policy installed extensions," and a
   blocking handler needs both `webRequest` and `webRequestBlocking` in the manifest. This
   restriction is a named-scope exception, not a version-dependent one; nothing in the packet
   changes it.
   *Do differently:* treat blocking webRequest as viable only for enterprise/policy deployment,
   and use DNR for store-distributed extensions.

5. **(05158f86)** Before Chrome 120, an extension could ship 50 static rulesets with 10 enabled
   simultaneously; Chrome 120 raised this to 50 enabled out of 100 total. The post also notes
   this exceeds the WECG-requested limit of 20, and that Firefox and Safari support the increase.
   *Do differently:* an extension architecture that split lists to stay under 10 enabled rulesets
   can be collapsed on Chrome 120+.

6. **(2741637b + a65606cd, combined)** The dynamic rule ceiling is conditional on rule action,
   not a single number. From Chrome 121, 30,000 rules are available for "safe" rules — defined
   as `block`, `allow`, `allowAllRequests`, `upgradeScheme` — exposed as
   `MAX_NUMBER_OF_DYNAMIC_RULES`; all other dynamic rules remain capped at 5,000
   (`MAX_NUMBER_OF_UNSAFE_DYNAMIC_RULES`). a65606cd adds that unsafe rules added within the
   5,000 allowance also count against the 30,000 total.
   *Do differently:* budget rules by action type, and expect a redirect- or modifyHeaders-heavy
   ruleset to hit 5,000 long before 30,000.

7. **(a65606cd)** Session rules are a separate 5,000 bucket (`MAX_NUMBER_OF_SESSION_RULES`).
   Before Chrome 120 the 5,000 was a *combined* dynamic-and-session limit; a65606cd states this
   twice, so the split is unambiguous.
   *Do differently:* on Chrome 120+, do not subtract session rules from the dynamic budget.

8. **(a65606cd)** The phrasing is a floor, not a fixed value: "at least 5000 dynamic rules."
   Code should read the exposed constants rather than hardcoding 5,000 or 30,000.
   *Do differently:* read `MAX_NUMBER_OF_*` at runtime.

9. **(05158f86, 2741637b vs. 095a5599, 79250f1d, f67dbbf9)** Two sources in this packet are
   superseded by later ones in the same packet: f67dbbf9's June-2025 enterprise horizon is
   overtaken by 79250f1d, and 05158f86's "until recently ... 10 of these enabled" describes a
   pre-Chrome-120 state. 2741637b and a65606cd agree on the Chrome 121 split, so the DNR
   dynamic-rule account is corroborated rather than contested.
   *Do differently:* date-check any DNR or MV2 answer against Chrome 120/121/138/139 before
   relying on it.

## What you could not determine

- **Regex rule limits.** The packet never mentions `regexFilter`, regex rule counts, or any
  separate regex ceiling (static or dynamic). Whether ~4,000 regex rules are permitted cannot
  be settled here.
- **Static rule count limits.** The packet gives ruleset *counts* (50/100) but never the number
  of rules permitted inside a static ruleset, nor the guaranteed/global static rule limits.
- **Remote code execution.** Nothing in the packet addresses hosted/remote code, `eval`, or the
  MV3 policy on executing code fetched at runtime.
- **Review timelines.** No source discusses Chrome Web Store review, expedited review for
  ruleset-only updates, or what would make such an expectation hold.
- **What enterprises should do after Chrome 139.** The sources state the policy is removed; they
  do not describe any successor policy, extended-support channel, or migration path.
- **Exact behaviour of `ExtensionManifestV2Availability` between March and July 2025.** 095a5599
  says "at least June 2025" and that the 139 branch begins in June; 79250f1d says the policy is
  removed with 139. The packet does not pin the stable-release date of Chrome 139.
