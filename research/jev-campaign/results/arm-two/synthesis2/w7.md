## Summary

The packet covers two distinct regimes: the removal of Manifest V2 support from Chrome, and the numeric limits that govern declarativeNetRequest (DNR) rules in Manifest V3. On MV2, two snapshots of the same document (095a5599, 2025-03-31; 79250f1d, 2025-07-24) describe a staged withdrawal in which the enterprise `ExtensionManifestV2Availability` policy is the last surviving exception — an exception scoped to enterprises and to Chrome 138 and earlier, removed outright in Chrome 139. The earlier snapshot is superseded in part (its "exempt until at least June 2025" and "users can turn extensions back on" statements no longer describe the current state) but its identification of Chrome 138 as the final MV2-supporting version still holds under the later one. On DNR, a 2023 blog post (05158f86, 2741637b) announces limit increases shipping in Chrome 120 and 121, and the 2025 API reference (7c82d4f5, a65606cd) confirms those increases landed as stated — so the blog's *old* figures (10 enabled rulesets of 50; a single 5,000 combined dynamic+session ceiling) are now historical and only correct for pre-120 Chrome. The raised dynamic ceiling is conditional: it applies only to a named "safe" action set, while everything else, including redirect, stays at 5,000. One restriction survives every change untouched: blocking `webRequest` listeners in MV3 are available only to policy-installed extensions (688c66f7).

## Findings

1. **(095a5599 + 79250f1d, combined)** The enterprise `ExtensionManifestV2Availability` policy is a genuine but time-boxed exception: it keeps MV2 extensions working on Chrome 138, and is removed in Chrome 139, at which point MV2 extensions cease to function for every user at once rather than via a gradual rollout. Both sources agree Chrome 138 is the last MV2-supporting version. *Consequence:* an enterprise planning MV2 continuity should treat the Chrome 139 branch as a hard cutover date, not a deadline that can be extended by policy.

2. **(095a5599 vs. 79250f1d)** Two claims in the March 2025 snapshot are superseded by the July 2025 snapshot: that users "continue to be able to turn their Manifest V2 extensions back on" (79250f1d: "Users can no longer turn them back on" as of Chrome 138), and that enterprises are exempt "until at least June 2025" (79250f1d states the policy is removed with Chrome 139). *Consequence:* anyone answering from the March text alone would wrongly tell users a re-enable toggle still exists.

3. **(05158f86 + 7c82d4f5, combined)** The static-ruleset increase announced for Chrome 120 — 100 rulesets shipped, 50 enabled simultaneously, up from 50 shipped / 10 enabled — is confirmed as current in the 2025 API reference, which names `MAX_NUMBER_OF_ENABLED_STATIC_RULESETS` (50) and a `GUARANTEED_MINIMUM_STATIC_RULES` of 30,000. *Consequence:* the pre-120 figures of 50/10 are correct only as history and should not be used to size a shipping extension.

4. **(2741637b + a65606cd, combined)** The 30,000-rule dynamic ceiling (`MAX_NUMBER_OF_DYNAMIC_RULES`, from Chrome 121) is scoped to "safe" rules, defined exhaustively as actions `block`, `allow`, `allowAllRequests` and `upgradeScheme`. All other dynamic rules remain capped at 5,000 (`MAX_NUMBER_OF_UNSAFE_DYNAMIC_RULES`), and unsafe rules added within that 5,000 also count against the 30,000. *Consequence:* a developer budgeting rules must classify by action first — an action outside the four-item list buys no headroom at all.

5. **(a65606cd)** Session rules are a separate 5,000-rule pool (`MAX_NUMBER_OF_SESSION_RULES`); the pre-Chrome-120 rule that dynamic and session rules shared one combined 5,000 limit no longer applies. *Consequence:* on Chrome 120+ an extension can hold session and dynamic rules concurrently without them competing for the same budget.

6. **(7c82d4f5)** Regex rules are capped independently of the overall static budget: at most 1,000 regex rules *of each type* (`MAX_NUMBER_OF_REGEX_RULES`), and every rule must be under 2KB once compiled. *Consequence:* a large regex-based ruleset has to be rewritten into non-regex matching patterns rather than split across more rulesets, since the regex cap is not relieved by the 30,000-rule static guarantee.

7. **(688c66f7)** In MV3, `webRequestBlocking` — required to register blocking event handlers, alongside the `webRequest` permission — is available only to policy-installed extensions. This restriction is stated as of February 2025 and nothing in the packet modifies it. *Consequence:* a store-distributed MV3 extension must use declarativeNetRequest for blocking; only a fleet that can force-install by policy has the blocking webRequest path.

8. **(05158f86)** The Chrome ruleset limits were set above the WECG's requested limit of 20 enabled rulesets, and the increase had early input and support from Firefox and Safari. *Consequence:* a developer targeting multiple browsers can expect directional agreement on raised ruleset limits, though the packet gives no other browser's actual numbers.

## What you could not determine

- **Remote code / runtime code execution.** The packet says nothing about whether MV3 extensions may fetch and execute code from a developer's server, nor about any remotely-hosted-code policy.
- **Extension review timing.** Nothing in the packet addresses review durations, expedited review for rule-file-only updates, or what makes a review fast or slow.
- **The exact Chrome version where MV2 disabling reached all channels.** 095a5599 (March 2025) already says all users on all channels have MV2 disabled by default, while 79250f1d attaches "all users on all channels" to Chrome 138; the packet does not reconcile the version numbering of the intervening rollout.
- **Whether other browsers removed MV2.** Firefox and Safari are mentioned only as supporting the DNR limit increase; their MV2 status is not covered.
- **Post-139 behaviour of the policy key.** Both sources say the policy is removed with Chrome 139; neither describes any replacement mechanism or transition tooling.
- **Whether the 30,000 `GUARANTEED_MINIMUM_STATIC_RULES` figure is a floor with a higher effective ceiling.** 7c82d4f5 calls it a guaranteed minimum but the packet does not state what, if anything, lies above it.

Once the fleet moves to Chrome 139 the policy is removed and MV2 support is gone from the browser, affecting all users on 139 simultaneously, so those extensions cease to function.
Sources: 095a5599, 79250f1d.

**Q2.** No. Redirect is not among the actions Chrome defines as "safe" (`block`, `allow`, `allowAllRequests`, `upgradeScheme`), so redirect rules fall under `MAX_NUMBER_OF_UNSAFE_DYNAMIC_RULES` — at least 5,000 dynamic rules — rather than the 30,000 `MAX_NUMBER_OF_DYNAMIC_RULES` ceiling available from Chrome 121 for safe rules; those unsafe rules also count toward the 30,000 total.
Sources: 2741637b, a65606cd.

**Q3.** No. The total number of regular expression rules of each type cannot exceed 1,000 (`MAX_NUMBER_OF_REGEX_RULES`), so 4,000 is not allowed; additionally each rule must be less than 2KB once compiled, and regex rules are permitted across all rule types.
Sources: 7c82d4f5.

Sources: 688c66f7.
