## Summary

The packet covers two separable regimes: the Manifest V2 deprecation timeline and the
declarativeNetRequest / webRequest rule and permission limits. On the MV2 side, three
sources form a supersession chain (f67dbbf9 2023-11 → 095a5599 2025-03-31 → 79250f1d
2025-07-24) in which the enterprise `ExtensionManifestV2Availability` exemption is
progressively narrowed and finally terminated: the earliest source promises an exemption
"until June 2025" that later sources overtake, so answering from f67dbbf9 alone gives a
wrong present-tense answer. On the limits side, the 2023-11 blog posts (05158f86, 2741637b)
announce raises that the 2025-06 API reference (a65606cd) confirms as current, with the
important qualification that the raised dynamic-rule ceiling is scoped to an enumerated set
of "safe" actions and the old 5,000 limit survives intact for everything else. The one
permission restriction in the packet — blocking webRequest — is not relaxed anywhere: it
survives into MV3 scoped to policy-installed extensions only.

## Findings

1. **f67dbbf9 + 095a5599 + 79250f1d (combination).** The enterprise policy exemption is
   described three times with a moving endpoint: f67dbbf9 grants "one additional year -
   until June 2025"; 095a5599 restates exemption "until at least June 2025" and names
   Chrome 138 as the last MV2-supporting version when paired with the policy key; 79250f1d
   states the policy "will be removed with Chrome 139." Anyone relying on the 2023-11 text
   alone would plan migration to a June-2025 calendar date rather than to a Chrome version
   boundary.

2. **095a5599 + 79250f1d (combination).** Non-enterprise state changed between the two
   dates: 095a5599 says MV2 extensions are disabled by default but "users continue to be
   able to turn their Manifest V2 extensions back on"; 79250f1d says that with Chrome 138
   "users can no longer turn them back on." A support answer written from the March source
   would wrongly tell an ordinary user a re-enable toggle exists.

3. **095a5599 + 79250f1d.** Both agree the 139 change is simultaneous, not staged — it
   "will impact all users on Chrome 139 at once" / "affect all users on Chrome 139
   simultaneously," explicitly unlike the earlier gradual rollouts. A fleet planning a
   phased cutover should treat 138→139 as a single cliff, not a ramp.

4. **2741637b + a65606cd (combination).** The 30,000-rule dynamic limit is scoped by
   action, not by extension: it applies only to rules whose action is `block`, `allow`,
   `allowAllRequests` or `upgradeScheme` (2741637b), while "the rule limit for all other
   dynamic net request rules stays at 5,000" (2741637b), which a65606cd exposes as
   `MAX_NUMBER_OF_UNSAFE_DYNAMIC_RULES` and notes that unsafe rules within that 5,000 also
   count toward the 30,000. A developer must count rules by action type before assuming
   headroom, and budget unsafe rules against both ceilings.

5. **05158f86.** The static-ruleset limits changed in Chrome 120: previously 50 lists
   shipped with 10 enabled simultaneously; now up to 50 enabled simultaneously and 100
   rulesets in total. An extension previously partitioning lists to stay under 10 enabled
   can stop doing so on Chrome 120+.

6. **a65606cd.** The dynamic/session accounting changed at Chrome 120: before 120 there was
   a single 5,000 combined dynamic-and-session limit; now session rules have their own
   5,000 (`MAX_NUMBER_OF_SESSION_RULES`) separate from the dynamic allowance. An extension
   that previously had to trade session rules off against dynamic ones no longer does.

7. **688c66f7.** Blocking webRequest survived into MV3 but only within a named scope:
   `webRequestBlocking` "is only available to policy installed extensions," and a blocking
   handler requires both `webRequest` and `webRequestBlocking` in the manifest. A
   Web-Store-distributed MV3 extension must use declarativeNetRequest instead; an
   enterprise force-installed one need not.

8. **05158f86.** The Chrome limit increase is stated to exceed the cross-browser request —
   "significantly higher than the limit of 20 requested in the WECG" — with Firefox and
   Safari supporting increases. A developer targeting multiple browsers should not assume
   Chrome's 50-enabled figure is portable.

## What you could not determine

- Whether Chrome 139 shipped as described: 79250f1d (2025-07-24) states the removal in the
  future tense, and the packet contains no later source confirming it happened.
- Any static-rule limits by count, and anything at all about regex-based rules — the packet
  gives ruleset counts (05158f86) and dynamic/session rule counts (2741637b, a65606cd) but
  no per-ruleset rule totals and no regex rule ceiling, pattern-length limit or
  memory constraint.
- Remotely hosted code: the packet says nothing about running code fetched at runtime.
- Web Store review times or what a rules-only update implies for review.
- Whether users on Chrome versions before 138 retain the re-enable toggle described in
  095a5599, and what happens to the `ExtensionManifestV2Availability` policy key itself in
  managed-policy tooling after its removal.
- Whether `redirect`, `modifyHeaders` or other actions have limits other than the residual
  5,000 — the sources define the safe set positively and lump the rest together without
  enumerating them.

extensions (when paired with the ExtensionManifestV2Availability key)." On Chrome 139 the
policy is removed (79250f1d) and MV2 extensions cease to function, for all users at once
rather than by gradual rollout. Sources: 095a5599, 79250f1d (and f67dbbf9 for the superseded
"until June 2025" framing).

ceiling does not cover them, and unsafe rules within 5,000 also count toward the 30,000.
Sources: 2741637b, a65606cd.
