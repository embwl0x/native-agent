## Summary

The packet covers two distinct regimes: the Manifest V2 deprecation timeline and the
declarativeNetRequest / webRequest rule-and-permission limits. Both are staged over Chrome
versions, and in both cases the packet contains an older statement that has since been
overtaken by a newer one from the same product line. On MV2, the enterprise
`ExtensionManifestV2Availability` policy is a scoped exception that repeatedly moved: a 2023
blog post grants enterprises an extra year to June 2025, a March 2025 timeline entry repeats
that and names Chrome 138 as the last supporting version, and a July 2025 entry states the
policy itself is removed in Chrome 139 and MV2 stops working for everyone at once. On rules,
Chrome 120 raised the simultaneously-enabled static ruleset count from 10 (of 50) to 50 (of
100) and ended the combined dynamic+session 5,000 cap, and Chrome 121 introduced a
two-tier dynamic limit where 30,000 applies only to an enumerated set of "safe" actions while
everything else remains at 5,000. The packet does not cover static rule counts, regex rules,
remotely hosted code, or store review timing.

## Findings

1. **Chrome 138 is the last version on which MV2 extensions run, and only under the
   enterprise policy** (095a5599, and 79250f1d together). 095a5599 states Chrome 138 is the
   final version to support MV2 "when paired with the `ExtensionManifestV2Availability` key";
   79250f1d states the policy is removed with Chrome 139 and MV2 extensions cease to function
   for anyone upgrading. This finding rests on the combination of both sources: neither alone
   states both the last supported version and the policy's removal. → A fleet that needs MV2
   to keep working must hold at 138 rather than plan a migration window after 139.

2. **The Chrome 139 cutoff is simultaneous, not a staged rollout** (095a5599, 79250f1d).
   Both say the change hits all users on Chrome 139 at once, explicitly contrasted in 095a5599
   with the earlier gradual disabling. → Migration planning cannot rely on a percentage
   rollout or on being in a late cohort.

3. **The June 2025 enterprise exemption in the 2023 blog post is no longer the current
   position** (f67dbbf9 superseded by 095a5599 and 79250f1d). f67dbbf9 (2023-11) promises
   enterprises "one additional year - until June 2025"; 095a5599 (2025-03-31) restates it as
   "until at least June 2025" and adds the Chrome 139 branch; 79250f1d (2025-07-24) removes the
   policy outright. This rests on all three sources read in date order. → Anyone answering from
   f67dbbf9 alone would give an exemption end date without knowing the policy key itself
   disappears.

4. **Whether a user can re-enable a disabled MV2 extension changed between the two timeline
   snapshots** (095a5599 vs 79250f1d). 095a5599 says users "continue to be able to turn their
   Manifest V2 extensions back on"; 79250f1d says that as of Chrome 138 "Users can no longer
   turn them back on." The later source governs. → A support answer citing the re-enable toggle
   is wrong for Chrome 138 and later.

5. **The 30,000 dynamic-rule limit is scoped to an enumerated set of actions, not to dynamic
   rules generally** (2741637b, a65606cd). 2741637b defines "safe" as rules with an action of
   `block`, `allow`, `allowAllRequests` or `upgradeScheme`, and says the limit for all other
   dynamic rules "stays at 5,000"; a65606cd gives the two constants,
   `MAX_NUMBER_OF_UNSAFE_DYNAMIC_RULES` (5,000) and `MAX_NUMBER_OF_DYNAMIC_RULES` (30,000), and
   adds that unsafe rules added within the 5,000 also count toward the larger limit. The
   action-list and the constant names come from different sources, so this rests on both.
   → An extension using any action outside that list must budget against 5,000, not 30,000.

6. **The static ruleset limits changed in Chrome 120: 10-of-50 became 50-of-100** (05158f86).
   The source states the prior regime (50 offered, 10 enabled simultaneously), the new one (50
   enabled, 100 total) and that it ships in Chrome 120, noting this exceeds the WECG-requested
   20. → A filtering extension can ship and enable far more lists than the pre-120 design
   allowed, provided it targets Chrome 120+.

7. **Before Chrome 120 dynamic and session rules shared one 5,000 budget; afterwards session
   rules have their own 5,000** (a65606cd). The source states the combined pre-120 limit twice
   and gives `MAX_NUMBER_OF_SESSION_RULES` as 5,000. → Post-120 code can hold 5,000 session
   rules without eating into the dynamic allowance.

8. **Blocking webRequest survives into MV3 only for policy-installed extensions**
   (688c66f7). `webRequestBlocking` is required to register blocking handlers and, as of MV3,
   "is only available to policy installed extensions"; both `webRequest` and
   `webRequestBlocking` must be declared. → A store-distributed MV3 extension must use
   declarativeNetRequest; an enterprise-deployed one may still block.

## What you could not determine

- Static rule count limits, regex rule limits, or any constraints specific to regex-based
  rules. The packet discusses static *rulesets* (05158f86) and dynamic/session rule counts
  (2741637b, a65606cd) but never static rule counts or regex.
- Remotely hosted code: nothing in the packet addresses running code fetched at runtime, or
  any exception to such a rule.
- Chrome Web Store review times, and whether a rules-only update is treated differently.
- Whether the 05158f86 ruleset limits and the 2741637b/a65606cd dynamic limits were still
  current as of the packet's latest sources — a65606cd (2025-06) restates the Chrome 121
  behaviour, but no source after 2023-11 restates the ruleset counts.
- What happens to enterprises that were relying on the policy after Chrome 139 — the packet
  states the policy is removed but describes no replacement or successor mechanism.
- Whether the "safe" action list in 2741637b is exhaustive for all time, or was defined only
  as of Chrome 121.
