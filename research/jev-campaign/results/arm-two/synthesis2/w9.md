## Summary

The packet covers two distinct regimes: the Manifest V2 phase-out timeline for Chrome, and the
rule-count limits of the `declarativeNetRequest` (DNR) API in Manifest V3. In both areas the
packet contains sources that were superseded by later ones, so a correct answer depends on
knowing which source is current. For MV2, the 2023 announcement (f67dbbf9) granted enterprises
using the `ExtensionManifestV2Availability` policy an exemption "until June 2025"; the 2025
update (095a5599) is the current source and converts that open-ended date into a hard version
boundary — Chrome 138 is the last version that honours the policy, and Chrome 139 removes MV2
support for everyone at once. For DNR, the limits were raised twice (Chrome 120 for rulesets,
Chrome 121 for dynamic rules), and the raised dynamic limit is an exception that holds only
within a named scope: the four "safe" rule actions. Rules outside that scope remain capped at
the old 5,000. One convenience — review skipping in minutes — is likewise scoped to "safe"
modifications of static rule lists. Several questions the packet raises (regex rule limits,
remote code execution) are not addressed by any source here.

## Findings

1. **(f67dbbf9 + 095a5599, combination)** The enterprise policy exemption was never a permanent
   carve-out and has now been given a version boundary. f67dbbf9 (2023-11) promised policy-using
   enterprises "one additional year - until June 2025"; 095a5599 (2025-03-31) states that the
   exemption runs "until at least June 2025", that the Chrome 139 branch begins in June, and that
   "Chrome 138 is the final version of Chrome to support Manifest V2 extensions (when paired with
   the `ExtensionManifestV2Availability` key)." *Consequence:* an enterprise planning migration
   should treat 138, not a calendar date, as the pin point, and must not assume the policy will
   carry MV2 into 139.

2. **(095a5599)** The MV2 removal in Chrome 139 is described as behaving differently from the
   earlier disablement: "Unlike the previous changes to disable Manifest V2 extensions which
   gradually rolled out to users, this change will impact all users on Chrome 139 at once."
   *Consequence:* a fleet cannot rely on staged rollout to buy time or to detect breakage early.

3. **(095a5599)** A restriction that survived the change with a user escape hatch: MV2 extensions
   are already "disabled by default" on all channels, but "users continue to be able to turn their
   Manifest V2 extensions back on." That escape hatch is a property of the disablement phase, not
   of the 139 removal. *Consequence:* support teams should not treat "users can re-enable it" as
   a workaround that will still exist after 139.

4. **(05158f86)** The static ruleset limits were raised in Chrome 120: previously "50 lists (or
   'static rulesets')" with "10 of these to be enabled simultaneously"; now "up to 50 to be enabled
   simultaneously" and "100 rulesets in total." *Consequence:* an extension that shipped a
   10-enabled-ruleset design for compatibility reasons can widen it, but only on Chrome 120+.

5. **(2741637b + a65606cd, combination)** The raised dynamic rule limit is an exception scoped to
   an enumerated set of actions, not a general increase. 2741637b: "Starting with Chrome 121, the
   higher limit of 30,000 rules applies to safe DNR rules, which we are defining as rules with an
   action of `block`, `allow`, `allowAllRequests` or `upgradeScheme`. [...] The rule limit for all
   other dynamic net request rules stays at 5,000." a65606cd names the two constants:
   `MAX_NUMBER_OF_UNSAFE_DYNAMIC_RULES` (at least 5000) and `MAX_NUMBER_OF_DYNAMIC_RULES` (30,000
   for safe rules), and adds the interaction rule: "Any unsafe rules added within the limit of 5000
   will also count towards this limit." *Consequence:* a developer budgeting rules must classify
   each rule by action before counting, and must subtract unsafe rules from the 30,000 headroom
   rather than treating the two pools as additive.

6. **(a65606cd)** Session rules are a separate pool of 5,000 (`MAX_NUMBER_OF_SESSION_RULES`), and
   this is itself a post-change state: "Before Chrome 120, there was a limit of 5000 combined
   dynamic and session rules." *Consequence:* on Chrome 120+ a developer can use both pools fully
   rather than splitting a single shared 5,000 budget.

7. **(688c66f7)** A blocking `webRequest` listener is still possible under MV3 but only inside a
   named scope: `webRequestBlocking` is "Required to register blocking event handlers. As of
   Manifest V3, this is only available to policy installed extensions," and the manifest needs both
   `"webRequest"` and `"webRequestBlocking"`. *Consequence:* a blocking-webRequest design is viable
   only for an extension distributed by enterprise policy, not for a Web Store extension.

8. **(e8621005)** Review skipping is conditional on both the kind of change and the rule list it
   touches: "If the only changes are for safe modifications to an extension's static rule list for
   declarativeNetRequest, Chrome will approve the update in minutes." *Consequence:* a filter-list
   publisher can plan rapid list refreshes, but must keep code changes out of those updates or lose
   the fast path.

9. **(e8621005 vs. 2741637b/a65606cd, combination — apparent tension)** e8621005 (2024-05)
   summarises the limits as "bundle up to 330,000 static rules and dynamically add a further
   30,000," stating the 30,000 dynamic figure without the safe/unsafe qualifier that 2741637b
   (2023-11) introduced and a65606cd (2025-06, the most recent DNR source) still carries.
   *Consequence:* a developer sizing a ruleset should take the number from the API reference
   a65606cd and its qualifier, not from the blog's unqualified summary.

## What you could not determine

- **Regex rules.** No source in the packet mentions regex-based filter rules, a separate regex
  rule limit, or any constraint specific to them (such as pattern length or memory cost).
- **Remote code / hosted code.** No source addresses whether an MV3 extension may fetch and run
  code from a remote server, or what the permitted alternatives are.
- **What counts as a "safe modification"** for review-skipping purposes. e8621005 uses the phrase
  but does not define it, and the only definition of "safe" in the packet (2741637b) is about
  *dynamic* rule actions, not about static-list edits.
- **The 330,000 static rule figure.** e8621005 gives it, but no source in the packet states the
  Chrome version it landed in, whether it is per-extension or per-ruleset, or how it interacts with
  the 100-ruleset / 50-enabled ceiling in 05158f86.
- **Post-139 enterprise options.** 095a5599 says support is removed in 139; the packet does not say
  whether any policy, channel, or extended-support build remains for enterprises after that.
- **Firefox and Safari specifics.** 05158f86 says both "provided early input" and support the
  increased limits, but the packet gives no actual Firefox or Safari limit values or timelines.

## Frozen question set

**Q1.** Yes — their MV2 extensions run on Chrome 138, because the `ExtensionManifestV2Availability`
policy exemption holds through 138, which 095a5599 calls "the final version of Chrome to support
Manifest V2 extensions (when paired with the ExtensionManifestV2Availability key)." Once the fleet
moves to Chrome 139 the extensions stop working: MV2 support is removed from Chrome in the 139
branch and the change "will impact all users on Chrome 139 at once," with no policy carve-out.
Sources: 095a5599 (current), f67dbbf9 (superseded — its "until June 2025" framing predates the
version boundary).

**Q2.** No. `redirect` is not among the four actions defined as safe (`block`, `allow`,
`allowAllRequests`, `upgradeScheme`), so redirect rules fall under "all other dynamic net request
rules," whose limit "stays at 5,000" — exposed as `MAX_NUMBER_OF_UNSAFE_DYNAMIC_RULES`. The 30,000
`MAX_NUMBER_OF_DYNAMIC_RULES` ceiling (Chrome 121+) does not lift this, and any unsafe rules added
within the 5,000 also count against the 30,000. So ~12,000 dynamic redirect rules is not possible.
Sources: 2741637b, a65606cd.

**Q6.** Before Chrome 120, 10 static rulesets could be enabled simultaneously, out of 50 shipped
("we allowed each extension to offer users a choice of 50 lists (or 'static rulesets'), and for 10

Source: 05158f86.

**Q7.** Minutes — "If the only changes are for safe modifications to an extension's static rule
list for declarativeNetRequest, Chrome will approve the update in minutes." Whether the expectation
holds depends on the update containing nothing but safe modifications to the static DNR rule list;
any other change takes it off the review-skipping path. The packet does not define what makes a
static-list modification "safe." Source: e8621005.
