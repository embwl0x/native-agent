# Document S04

## Summary

The packet covers two distinct regulated areas of Chrome extensions: the Manifest V2
deprecation timeline, and the numeric limits on declarativeNetRequest (DNR) rules and
rulesets. In both areas the packet contains superseded and current sources side by side.
The MV2 thread runs from a 2023-11 announcement (f67dbbf9) that granted enterprises using
the `ExtensionManifestV2Availability` policy an extra year, to a 2025-03 update (095a5599)
that named Chrome 138 as the final MV2-capable version, to a 2025-07 update (79250f1d)
confirming the policy itself is removed in Chrome 139 — so the enterprise exemption is a
scoped, time-limited carve-out that has now expired, and an answer resting on f67dbbf9
alone would be wrong. The DNR thread shows limits being raised (rulesets in Chrome 120,
safe dynamic rules in Chrome 121) while the older, lower limit *survives* for everything
outside the named "safe" action set — an exception defined by rule action, not by
extension. The packet also shows one restriction that did not loosen at all: blocking
`webRequest` listeners remain available only to policy-installed extensions under MV3.
Several things the frozen question set asks about — regex rule limits, static rule counts,
remotely hosted code, and review timelines — are simply not in the packet.

## Findings

1. **The enterprise MV2 exemption was scoped to a deadline, and that deadline has passed.**
   Rests on f67dbbf9 (2023-11) *combined with* 095a5599 (2025-03) and 79250f1d (2025-07).
   f67dbbf9 grants policy-using enterprises "one additional year - until June 2025";
   095a5599 says the exemption holds "until at least June 2025" and that the Chrome 139
   branch begins in June; 79250f1d states the policy "will be removed with Chrome 139."
   Someone relying on f67dbbf9 alone would plan a migration that is already overdue and
   would assume a policy escape hatch that no longer exists.

2. **Chrome 138 is the last version on which MV2 extensions can run, and only via the
   policy.** Rests on 095a5599 and 79250f1d together. 095a5599: "Chrome 138 is the final
   version of Chrome to support Manifest V2 extensions (when paired with the
   ExtensionManifestV2Availability key)." 79250f1d: at Chrome 138 ordinary users can no
   longer turn MV2 extensions back on. An admin would pin the fleet at 138 to buy time,
   and would treat any 139 upgrade as a hard cutoff rather than a gradual rollout.

3. **The Chrome 139 change is discontinuous, not a staged rollout.** Rests on 095a5599
   ("this change will impact all users on Chrome 139 at once") and 79250f1d ("will affect
   all users on Chrome 139 simultaneously"). A team would not plan on a percentage
   rollout, a holdback, or a staged recovery window.

4. **The raised dynamic-rule limit is an exception scoped by rule action, and the old
   5,000 limit survives for everything else.** Rests on 2741637b *combined with*
   a65606cd. 2741637b: from Chrome 121 the 30,000 limit applies to "safe" rules, defined
   as actions `block`, `allow`, `allowAllRequests` or `upgradeScheme`, and "the rule limit
   for all other dynamic net request rules stays at 5,000." a65606cd names the two
   constants — `MAX_NUMBER_OF_UNSAFE_DYNAMIC_RULES` (at least 5,000) and
   `MAX_NUMBER_OF_DYNAMIC_RULES` (30,000 from Chrome 121) — and adds that unsafe rules
   added within the 5,000 allowance also count toward the larger limit. A developer would
   budget rules by action type, not by a single total, and would not assume 30,000 is
   available to rules such as `redirect` or `modifyHeaders`.

5. **Session rules are capped separately at 5,000, and the older combined cap is now
   historical.** Rests on a65606cd. It gives `MAX_NUMBER_OF_SESSION_RULES` as 5,000 and
   states twice that "before Chrome 120, there was a limit of 5000 combined dynamic and
   session rules." A developer targeting Chrome 120+ would size dynamic and session rule
   sets independently rather than against one shared pool; one targeting older versions
   would not.

6. **The static-ruleset limits were raised in Chrome 120, and the pre-120 numbers are
   superseded.** Rests on 05158f86. Previously 50 rulesets shipped with 10 enabled
   simultaneously; from Chrome 120, up to 50 may be enabled and 100 may ship in total.
   The source also notes this is higher than the 20 requested in the WECG, and that
   Firefox and Safari supported raising the limits. A developer would restructure their
   list offering around 50 concurrently-enabled rulesets rather than 10.

7. **Blocking `webRequest` is not deprecated outright under MV3 — it is narrowed to a
   named install scope.** Rests on 688c66f7: `webRequestBlocking` is "only available to
   policy installed extensions" under MV3, and a blocking handler requires both
   `webRequest` and `webRequestBlocking` in the manifest. An enterprise-deployed extension
   could still use blocking interception; a Web Store extension would have to be rebuilt
   on declarativeNetRequest.

8. **Two restrictions in this packet are gated on policy/enterprise status, but they are
   independent gates with different fates.** Rests on 688c66f7 *combined with* 79250f1d.
   The `webRequestBlocking` carve-out (688c66f7, dated 2025-02) is stated without an end
   date, whereas the `ExtensionManifestV2Availability` carve-out ends at Chrome 139
   (79250f1d). Someone should not infer from the MV2 policy's removal that the
   policy-installed blocking webRequest exception also ends — the packet asserts no such
   link.

## What you could not determine

- Whether the `webRequestBlocking` exception for policy-installed MV3 extensions still
  holds after Chrome 139. 688c66f7 is dated 2025-02, earlier than 79250f1d (2025-07), and
  nothing in the packet updates it.
- Any limits on regex-based DNR rules, or on the number of rules within a static ruleset.
  The packet gives ruleset counts (05158f86) and dynamic/session rule counts (2741637b,
  a65606cd) but never static rule counts or any regex-specific constraint.
- Anything about remotely hosted code, the MV3 code-execution restrictions, or
  `userScripts`. Not present in any source here.
- Anything about Chrome Web Store review times or what influences them.
- Whether the 2023-11 statement in 05158f86 that the ruleset change "is shipping in
  Chrome 120" was borne out; no later source in the packet confirms it shipped as
  described.
- The exact meaning of "at least 5000 dynamic rules" in a65606cd — whether the floor is
  ever higher in practice is not stated.
- Whether MV2 extensions remained functional for enterprises between the 2025-03 statement
  ("until at least June 2025") and the Chrome 139 branch; the packet's "at least" leaves
  the end of that window imprecise, and 79250f1d resolves it only by naming the version,
  not a date.

## Frozen question set

**Q1.** Yes — on Chrome 138 with `ExtensionManifestV2Availability` set, the fleet's
Manifest V2 extensions still run; 095a5599 names Chrome 138 as "the final version of
Chrome to support Manifest V2 extensions (when paired with the ExtensionManifestV2Availability
key)." Once the fleet moves to Chrome 139 the policy is removed and MV2 support is gone,
and 79250f1d and 095a5599 both stress this hits all Chrome 139 users at once rather than
as a gradual rollout, so MV2 extensions cease to function on upgrade.
Sources: 095a5599, 79250f1d (and f67dbbf9 for the now-expired June 2025 exemption).

as `block`, `allow`, `allowAllRequests` and `upgradeScheme` and says "the rule limit for
all other dynamic net request rules stays at 5,000" — so redirect rules fall under
`MAX_NUMBER_OF_UNSAFE_DYNAMIC_RULES` (at least 5,000 per a65606cd), well short of 12,000.
The 30,000 `MAX_NUMBER_OF_DYNAMIC_RULES` ceiling from Chrome 121 governs safe rules only,
and a65606cd adds that unsafe rules within the 5,000 allowance also count toward it.
Sources: 2741637b, a65606cd.
