# Document S05

## 1. Summary

The packet documents two intertwined regimes: the Manifest V2 phase-out and the rule-count
limits of the declarativeNetRequest (DNR) API. On the phase-out, an earlier source (f67dbbf9,
2023-11) grants enterprises using the `ExtensionManifestV2Availability` policy an exemption
"until June 2025"; a later source (095a5599, 2025-03-31) supersedes that end-date with a
concrete version boundary — Chrome 138 is the last version that runs MV2 extensions when paired
with the policy, and Chrome 139 removes MV2 support for everyone at once. On DNR limits, the
packet records a sequence of loosenings (Chrome 120 raised simultaneously-enabled static rulesets
from 10 to 50 out of 100 total; Chrome 121 introduced a 30,000-rule ceiling for *safe* dynamic
rules) while a restriction survived each change: rules that are not `block`, `allow`,
`allowAllRequests` or `upgradeScheme` remain capped at 5,000. A separate narrow exception survives
the MV3 transition itself — blocking `webRequest` listeners still exist, but only for
policy-installed extensions. The packet also establishes a review-speed concession (minutes,
not days) scoped strictly to safe static-rule-list changes. Several questions the packet raises —
regex rule limits and remotely hosted code — it does not settle at all.

## 2. Findings

1. **Enterprise MV2 exemption is version-bounded, and the older statement of it is no longer
   current** (rests on the combination of f67dbbf9 + 095a5599). f67dbbf9 (2023-11) states the
   exemption runs "until June 2025"; 095a5599 (2025-03-31) restates it as "until at least June
   2025" and then fixes the boundary in versions: Chrome 138 is the final version to support MV2
   extensions when paired with the `ExtensionManifestV2Availability` key, and the Chrome 139
   branch removes MV2 support. Anyone answering from f67dbbf9 alone would give a date with no
   version, and would miss that the cutoff is a browser-version event rather than a calendar one.
   *Consequence:* an enterprise plans migration against a pin at 138, not against a June date.

2. **The MV2 disable-by-default rollout and the MV2 removal behave differently** (095a5599).
   The earlier disabling "gradually rolled out to users," whereas removal "will impact all users
   on Chrome 139 at once." *Consequence:* a fleet cannot rely on staged exposure to catch
   breakage before it is widespread; it must be migrated before the 139 branch reaches it.

3. **Users could re-enable disabled MV2 extensions; that workaround does not survive removal**
   (095a5599). As of 2025-03-31 MV2 extensions are disabled by default on all channels but
   "users continue to be able to turn their Manifest V2 extensions back on" — a statement made
   about the disable regime, not the 139 removal, which the same source describes as support
   being "removed from Chrome." *Consequence:* support guidance that tells users to flip the
   toggle stops being valid at 139.

4. **The 10-of-50 static ruleset limit changed in Chrome 120 to 50-of-100** (05158f86). Up to
   Chrome 120, an extension could offer 50 static rulesets with 10 enabled simultaneously;
   Chrome 120 allows 50 enabled simultaneously and 100 in total. The source notes this is
   "significantly higher than the limit of 20 requested in the WECG" and that Firefox and Safari
   also support raising the limits. *Consequence:* a filtering extension can ship and enable far
   more user-selectable lists, but only on Chrome 120+.

5. **A rule's *action* determines which dynamic ceiling applies, and the 5,000 cap survived the
   Chrome 121 increase** (rests on the combination of 2741637b + a65606cd). 2741637b defines
   "safe" DNR rules as those with an action of `block`, `allow`, `allowAllRequests` or
   `upgradeScheme`, gives them a 30,000 ceiling from Chrome 121 (`MAX_NUMBER_OF_DYNAMIC_RULES`),
   and states "the rule limit for all other dynamic net request rules stays at 5,000."
   a65606cd names that surviving cap `MAX_NUMBER_OF_UNSAFE_DYNAMIC_RULES` and adds that unsafe
   rules added within the 5,000 limit "also count towards" the 30,000 limit. *Consequence:* a
   developer budgets rules by action type and subtracts unsafe rules from the safe headroom,
   rather than treating 30,000 as a flat allowance.

6. **Dynamic and session rules were decoupled at Chrome 120** (a65606cd). Before Chrome 120
   there was a single 5,000 combined dynamic-and-session limit; afterwards session rules have
   their own 5,000 cap (`MAX_NUMBER_OF_SESSION_RULES`) alongside the dynamic limits.
   *Consequence:* on Chrome 120+ session rules no longer consume the dynamic budget.

7. **Blocking `webRequest` survives MV3 only inside a named scope** (688c66f7). The
   `webRequestBlocking` permission is "required to register blocking event handlers" and "as of
   Manifest V3, this is only available to policy installed extensions"; registering one requires
   both `webRequest` and `webRequestBlocking` in the manifest. *Consequence:* a
   store-distributed MV3 extension must use DNR instead, while an enterprise deploying by policy
   may keep a blocking listener.

8. **Review skipping is an exception scoped to safe static-rule changes only** (rests on the
   combination of e8621005 + 2741637b). e8621005 (2024-05) announces that if "the only changes
   are for safe modifications to an extension's static rule list for declarativeNetRequest,
   Chrome will approve the update in minutes"; the meaning of "safe" for DNR rules is supplied by
   2741637b's action list. *Consequence:* a filter-list publisher can ship list refreshes on a
   fast cadence, but any change touching code — or a rule with a non-safe action — falls back to
   ordinary review.

9. **The aggregate static/dynamic rule budget is stated once, in 2024** (e8621005). It reports
   extensions may "bundle up to 330,000 static rules and dynamically add a further 30,000." This
   is consistent with 2741637b's Chrome 121 safe-dynamic figure but is the packet's only source
   for the 330,000 static total. *Consequence:* a capacity plan for static rules rests on a
   single 2024 blog statement, with no API-reference confirmation in this packet.

10. **Version roll back exists as a deployment control** (e8621005). The source mentions "the
    launch of version roll back last month" as giving developers greater control over how updates
    deploy. *Consequence:* a developer shipping a risky update has a documented recovery path —
    though the packet gives no mechanics for it.

## 3. What you could not determine

- **Regex rules.** The packet never mentions regex-based filter rules, a
  `MAX_NUMBER_OF_REGEX_RULES` constant, or any regex-specific constraint (pattern length,
  compile budget, counting against static or dynamic limits). Nothing here settles whether a
  given number of regex rules is allowed.
- **Remotely hosted code.** The packet contains no statement about executing code fetched at
  runtime, the MV3 remotely-hosted-code policy, or permitted alternatives such as
  configuration-as-data. The MV3 sources here concern DNR limits, `webRequest` blocking and the
  MV2 timeline only.
- **Exact date/version mapping for Chrome 139.** 095a5599 says the 139 branch "will begin" in
  June 2025 and that 138 is the final supporting version, but the packet gives no stable-release
  date for 139 and no schedule for when a given fleet would receive it.
- **Whether the enterprise policy has any residual effect on 139.** 095a5599 says support is
  removed from Chrome in 139 and that 138 is final "when paired with the
  ExtensionManifestV2Availability key," which implies the policy stops helping; the packet does
  not state explicitly what the policy does, or whether it still exists, on 139+.
- **Whether the 330,000 static-rule figure (e8621005, 2024-05) is still current.** The newest
  DNR reference here (a65606cd, 2025-06) covers session and dynamic rules only and does not
  restate the static total, so the packet cannot confirm the 2024 number still holds.
- **Static ruleset limits after Chrome 120.** 05158f86 states the 50-enabled/100-total figures
  as shipping in Chrome 120; no later source in the packet reconfirms or revises them.
- **How the 30,000 safe-dynamic limit interacts with session rules.** a65606cd says unsafe
  dynamic rules count toward the 30,000 limit, but is silent on whether session rules do.
- **Scope of "safe modifications" for review skipping beyond rule actions.** e8621005 does not
  enumerate which static-rule-file edits qualify; 2741637b's definition is of safe *rules*, and
  the packet does not state that the two definitions are identical.
