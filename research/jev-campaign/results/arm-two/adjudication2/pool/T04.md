# Document T04
## Summary

The packet covers two distinct regulatory threads in Chrome's Manifest V3 transition: the timeline for removing Manifest V2 support (with a narrow enterprise-policy exemption that expires), and the numeric ceilings on declarativeNetRequest rules and rulesets (which were repeatedly raised, with the raises conditioned on rule *type*). The dominant pattern is that limits were relaxed but not uniformly: the increases are scoped to a named class of "safe" rules, while the older, lower ceiling survives intact for everything else. Likewise the MV2 enterprise exemption is scoped to a named policy key and a named end date, and one source in the packet (f67dbbf9, 2023-11) states an exemption horizon that a later source (095a5599, 2025-03) supersedes with a concrete removal mechanism. The webRequest blocking capability is not raised at all — it is restricted to a named installation scope and stays that way. Several of the frozen questions ask about areas (regex rule limits, remotely hosted code) that this packet simply does not cover.

## Findings

1. **Sources 05158f86 (2023-11) and e8621005 (2024-05).** The ruleset limits were raised twice in the packet's own telling, and along different axes: 05158f86 raises the *simultaneously enabled* static rulesets from 10 to 50 and the *total shipped* rulesets from 50 to 100, shipping in Chrome 120; e8621005 then describes the limits in terms of *rules* rather than *rulesets* — 330,000 static rules bundled plus 30,000 added dynamically. This is a combination finding: neither source alone gives both the ruleset counts and the rule counts. Someone budgeting a filter list would size against 100 rulesets / 50 enabled *and* the 330,000 static rule figure, rather than treating either as the single governing cap.

2. **Sources 2741637b and a65606cd.** The 30,000 dynamic rule limit is not a general raise — it applies only to rules whose action is `block`, `allow`, `allowAllRequests` or `upgradeScheme` ("safe" rules), from Chrome 121. The old 5,000 ceiling survived the change and still governs every other dynamic rule. a65606cd adds that unsafe rules added within the 5,000 allowance also count against the 30,000. This is a combination finding: 2741637b defines the safe-action list and the surviving 5,000 limit; a65606cd supplies the double-counting rule and the constant names. A developer would therefore check each rule's *action* before assuming headroom, and would not plan a large ruleset around redirect or modifyHeaders actions.

3. **Source a65606cd.** The two limits are exposed as different constants — `MAX_NUMBER_OF_UNSAFE_DYNAMIC_RULES` for the 5,000 floor and `MAX_NUMBER_OF_DYNAMIC_RULES` for the 30,000 safe-rule limit — and session rules have their own separate 5,000 cap (`MAX_NUMBER_OF_SESSION_RULES`). Before Chrome 120 dynamic and session rules shared one combined 5,000 budget; that combination no longer applies. Code reading a single constant to compute remaining capacity would be reading the wrong number for at least one rule class.

4. **Sources 2741637b and a65606cd, read together, are not fully consistent on constant naming.** 2741637b says the 30,000 safe-rule figure "is available in Chrome as the MAX_NUMBER_OF_DYNAMIC_RULES constant" and that all other dynamic rules stay at 5,000; a65606cd says an extension "can have at least 5000 dynamic rules... exposed as the MAX_NUMBER_OF_UNSAFE_DYNAMIC_RULES." The packet does not reconcile the phrase "at least 5000 dynamic rules" with the flat statement that non-safe rules are capped at 5,000. A developer should read the constants at runtime rather than hard-coding either figure.

5. **Source 688c66f7 (2025-02).** Blocking webRequest handlers were not removed in Manifest V3 — they were narrowed to a named installation scope: `webRequestBlocking` is "only available to policy installed extensions," and the listener still requires both `webRequest` and `webRequestBlocking` in the manifest. An extension distributed through the Web Store cannot rely on this path; one deployed by enterprise policy can.

6. **Sources f67dbbf9 (2023-11) and 095a5599 (2025-03), in combination.** The enterprise exemption is scoped to the `ExtensionManifestV2Availability` policy and to a date, and the packet contains both the older statement of that date and its successor. f67dbbf9 grants policy-using enterprises "one additional year - until June 2025"; 095a5599 restates the exemption as lasting "until at least June 2025" and then supplies the mechanism that ends it — the Chrome 139 branch beginning in June, with MV2 support removed. Anyone answering a 2025-or-later question from f67dbbf9 alone would state an exemption without knowing it terminates at a specific browser version.

7. **Source 095a5599.** The final MV2-supporting version is Chrome 138, and only "when paired with the ExtensionManifestV2Availability key" — the pairing is load-bearing, since for ordinary users MV2 extensions are already disabled by default on all channels (though users can re-enable them individually). The Chrome 139 removal is explicitly not a gradual rollout: it hits all users at once. A fleet would plan migration against a version pin, not a percentage rollout.

8. **Source e8621005 (2024-05).** Review skipping is scoped to a named change class: if the *only* changes are "safe modifications to an extension's static rule list for declarativeNetRequest," Chrome approves the update in minutes. The exception does not extend to other parts of the package. A developer would split rule-only updates from code updates into separate releases to keep the fast path.

## What you could not determine

- **Regex rules.** The packet never mentions regular-expression rules, a regex-specific ceiling, or whether regex rules count as "safe." 2741637b's safe-action list is defined by *action*, not by matcher type, so it does not settle the question either.
- **Remotely hosted code.** Nothing in the packet addresses executing code fetched at runtime, remote script loading, or any permitted alternative.
- **What "safe modifications" means for review skipping.** e8621005 uses the phrase without defining it; whether it maps exactly onto 2741637b's safe-action list (block/allow/allowAllRequests/upgradeScheme) is not stated anywhere in the packet.
- **Whether the static-ruleset counts and the static-rule count interact.** 05158f86 gives 100 total / 50 enabled rulesets; e8621005 gives 330,000 static rules. The packet does not say whether the rule total is per-ruleset, across enabled rulesets only, or across all shipped rulesets.
- **Current status after 2025-06.** The newest source is a65606cd (2025-06). The packet does not confirm that the Chrome 139 removal occurred as described, only that it was scheduled.
- **The reconciliation noted in Finding 4** — which constant actually holds which value in shipping Chrome.

## Frozen question set

**Q1.** On Chrome 138 with `ExtensionManifestV2Availability` set, yes — 095a5599 states Chrome 138 is the final version of Chrome to support Manifest V2 extensions when paired with that policy key. Once the fleet moves to Chrome 139, support for MV2 extensions is removed from Chrome and the change impacts all users on 139 at once, with no gradual rollout; the earlier "until June 2025" exemption in f67dbbf9 is the stale framing of the same deadline. *Sources: 095a5599, f67dbbf9.*

**Q2.** No, not as dynamic rules. The 30,000-rule ceiling applies only to "safe" dynamic rules, defined as those with an action of `block`, `allow`, `allowAllRequests` or `upgradeScheme`; redirect is not on that list, so redirect rules fall under the limit for all other dynamic rules, which stayed at 5,000 (`MAX_NUMBER_OF_UNSAFE_DYNAMIC_RULES`). Unsafe rules added within that 5,000 also count toward the 30,000 total. *Sources: 2741637b, a65606cd.*

**Q3.** CANNOT DETERMINE FROM THESE SOURCES.

**Q4.** Yes, but only in a narrow scope: `webRequestBlocking` is required to register blocking event handlers and, as of Manifest V3, is available only to policy-installed extensions; the listener also requires the `webRequest` permission alongside `webRequestBlocking` in the manifest. *Source: 688c66f7.*

**Q5.** CANNOT DETERMINE FROM THESE SOURCES.

**Q6.** Before Chrome 120, 10 static rulesets could be enabled simultaneously, out of 50 offered in total; Chrome 120 raised these to 50 enabled simultaneously out of 100 total. *Source: 05158f86.*

**Q7.** Minutes — Chrome approves the update via review skipping if the only changes are safe modifications to the extension's static rule list for declarativeNetRequest. The expectation holds only on that condition: any other change in the update takes it off the fast path, and the packet does not define which static-rule modifications count as "safe." *Source: e8621005.*
