## App-side mitigation follow-through

User requested a safe app-side fix for the reproduced observer teardown leak.
The integrated fix retains one Bots page after first visit, as Chat already
does, instead of destroying its text controls on every sidebar switch. Hidden
work and motion stop; pointer/keyboard/AX interaction is gated. The hidden Bots
prose preference cannot mask the active page's tint. Returning refreshes through
the watcher's initial event. No observer internals, private APIs or accessibility
settings are changed; this is a bounded lifecycle mitigation.

Independent experiment source: `docs/diagnostics/ChatUIWorkaroundProbe.swift`.

`MallocStackLogging=1`, inspect using `leaks <pid>`, and use the three controls

## Performance evidence and retained protections

- A three-second live sample captured 236 main-thread samples, 235 waiting for
  events. No active SwiftUI layout loop appeared in that idle window. This says
  nothing about worst-case typing/streaming frame times.
- Sampled physical footprint was approximately 1.2 GB, with a 1.5 GB peak.
  The leak scan enumerated approximately 979 MB of malloc allocations; these
  measures have different meanings. Neither total is itself a leak measurement.
- Draft text stays in `ChatComposerDraft`, read by `ChatComposerInput`.
  New routing/policy reads live in a separate child. No timers, blur layers,
  file reads, or repeat animations were added to the composer row.
- Streaming remains a leaf update through `ChatStreamingTailBox`; the cache
  is capped at eight entries. The transcript retains its bounded plain VStack
  window, avoiding the previously diagnosed lazy-layout feedback problem.
- Shared `GlassCard` has a material path for scrolling rows and an opaque
  Reduce Transparency fallback. The composer keeps its single glass surface.
  Mood tint retains one idempotent, tolerant 60-second timer and a monotonic
  filter; it is not a per-frame animation.
- Bots file observation is in a lifecycle-cancelled `liveTask`. Session drag
  monitors already have explicit teardown and deallocation cleanup.
- Bot conversations do not falsely display Chat's model: the compact control
  says “Bot model” and routes to Bots, where the bot's own model is edited.
  The ordinary model popup explains that changes apply to the next accepted
  Chat turn. Trust labels derive from saved policy; errors stay visible.

### Independent framework leak reproduction

`docs/diagnostics/ChatUIFrameworkProbe.swift` is a standalone SwiftUI app with 100
plain text rows, a selection toggle, and a button removing/restoring the scroll
view. It imports only AppKit/SwiftUI, has no NativeAgent runtime or data access,
and registers no custom observer. Build with:

```sh
swiftc -O -parse-as-library docs/diagnostics/ChatUIFrameworkProbe.swift -o /tmp/ChatUIFrameworkProbe
MallocStackLogging=1 /tmp/ChatUIFrameworkProbe
```

Attach an accessibility client, inspect once, then toggle the transcript off/on
three times with a fresh accessibility read after each action. Run `leaks <pid>`
before and afterward; quit the probe when finished. In the tested bundle launch,
PID 65816 reported 284 objects / 18,624 bytes before and 606 / 34,208 bytes after.
One new root group contained 100 NSArray instances, allocated by AppKit
`_NSAccessibilityRemoveAllObserversAndSendDestroyedNotification` through
`NSArray.initWithArray`, after standard SwiftUI `NSScrollView` teardown. This is
the same allocation family and framework owner reproduced earlier in NativeAgent.
Logs: `/tmp/nativeagent-framework-leaks-before.txt` and
`/tmp/nativeagent-framework-leaks-after.txt`. Probe source is retained; its process
was quit. Its scrolling trace had no commit over 16.7 ms, so it reproduced the
observer leak, not NativeAgent's original large layout workload.

Final app scan: 538 objects / 17,344 bytes, mostly the same observer array family
plus a small CFData root; `/tmp/nativeagent-window60-leaks.txt`. That non-stack-
logged scan is not proof of every allocation's origin, nor a growth comparison
against another process. The independently reproduced AppKit bug cannot be
repaired by releasing objects NativeAgent does not own. No private-API patch,
disabling accessibility, or false zero-leak claim was used to conceal it.
